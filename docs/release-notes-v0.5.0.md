> 这版做一件事：**装上之后会告诉你一次「已更新到 0.5.0」**，然后就再也不提了。

---

## 一、新增：更新提示（只弹一次）

装好或升级到 0.5.0 后，第一次启动 Salt Player 会在主窗口底部弹一条绿色提示：

> **模组 spw-folia 已更新至 0.5.0 版本（重要更新）**

就这么一次。**之后无论重启多少次、升到 0.5.1 还是 0.6.0，都不会再弹。**

### 为什么只弹一次

这个位置以前有过「插件已加载」的提示，在 v0.3.2 被删掉了 —— 因为**每次启动都弹一条成功提示是纯噪音**，
用户很快就会学会无视它，等到真有要紧事的时候也不会再看。那条规矩现在依然有效，所以这次加回来的
唯一理由是：它真的是**一次性**的，而且这一版确实值得你知道。

### 什么时候弹、什么时候不弹

| 情况 | 会不会弹 |
| --- | --- |
| 全新安装 0.5.0，第一次启动 | **弹** |
| 从任意旧版本（0.4.x 及更早）升级上来 | **弹** |
| 同一台机器第二次、第三次重启 | 不弹 |
| 未来的 0.5.1 / 0.6.0 等版本 | 不弹 |
| 插件因为 SPW 版本太老、或缺权限而没能起来 | 不弹（那种情况有专门的错误提示，不会假装「已更新」） |

### 如果你没看到它

两个可能：

1. **你之前已经见过它了** —— 弹过一次就会被记住，这是设计如此。
2. 提示弹出时你正好没在看屏幕，一闪就过了。**它不会重复，也不会补弹。**

这就是「只弹一次」的代价，我们选择它，是因为重复弹的代价更大。

## 附：给维护者的技术备注

上面是面向用户的内容。以下是实现与验证记录。

**为什么单独成对象**：判定与存储放在 `FoliaUpdateNotice` 里（`NOTICE_VERSION` 常量 + `shouldShow` +
`message` + 读/写标记），`FoliaPlugin.start()` 只负责「读标记 → 判定 → 弹 → 弹成功才写标记」。
判定能被单元测试直接驱动，不必启动 SPW。

**只弹一次靠两个条件同时成立**：

1. `PLUGIN_VERSION == NOTICE_VERSION`（`"0.5.0"` 是**钉死的常量，不跟随** `PLUGIN_VERSION`）——
   这条保证未来任何版本都不会误弹；将来若要再通知一次，只改这一个常量。
2. 持久化标记 `updateNoticeShownVersion != NOTICE_VERSION` —— 存的是**版本号**而不是布尔值，
   所以「再来一次」的场景不需要改存储格式。

**触发点在两道 gate 之后**：版本不支持或缺 `class-transform` 权限时 `start()` 已提前 `return`，
插件根本不可用，此时弹「已更新」是误导。

**写标记的顺序**：先 pop toast、成功后才写标记。反过来的话，一旦 toast 调用抛异常，标记已写、
用户却从没看见，就把「重复一次」换成了「永远看不到」。当前实现下，写盘失败会导致下次启动**再弹一次**
（见日志 `update notice: shown … marker NOT saved`）——这是刻意选择的失败方向。

**验证**：

- JVM 单测 **70 项全过**，其中 `FoliaUpdateNoticeTest` 13 项：首次弹 / 同版本不弹 / 旧版本标记仍弹 /
  未来版本一律不弹 / 空白标记视为未提示 / 带空格的标记仍算已提示 / 文案插值 / 常量钉死 /
  存储读写往返 / save 失败仍弹 / 配置层抛异常降级为未提示 / helper 为 null 不抛。
- **变异测试（门禁有牙的证明）**：把 `shouldShow` 的版本钉死去掉（等价于「每个版本都弹」），
  `never shows for any version other than the notice version` 立即失败；把读键改成与写键不一致，
  `what the write stores is what the read finds` 立即失败。两处都实测过，改回后复绿。
- 发布门禁 `node packaging/tools/verify-all.mjs` → **10/10 executed checks，36.9 s**（4 套件并发）。

### ⚠️ 真机冒烟抓到的缺陷（首发构建已废弃）

第一次真机安装时，**日志显示通知已发出、标记已落盘，用户却一次都没看到**。复盘出的时序：

```
22:43:53.099  插件 start
22:43:53.803  update notice: shown for 0.5.0 (marker saved)   ← toast 在这里发出
22:43:54.236  SPW 自己的 `App start` 日志才写出                ← 界面此时才构建
```

插件 `start()` 比宿主主界面就绪**早约 0.7 s**。在界面尚未构建时调用 `WorkshopApi.ui.toast`
**既不抛异常、也不排队、更不会补发** —— 它被宿主静默丢弃。由于代码在 toast 之后立刻写标记，
这一版会变成「通知永久作废、用户永远看不到」，而且**任何单元测试和发布门禁都发现不了**
（门禁只驱动打包页面，不驱动插件启动时序）。

**修复**：判定之后不再立刻弹，而是起一个 daemon 线程轮询 `Window.getWindows()`，等出现第一个
`isDisplayable && isShowing` 的窗口，再用 `SwingUtilities.invokeLater` 弹。上限 10 s、50 ms 一次，
**超时就不弹且不写标记**（下次启动还能补）。真机实测两次：`UI ready after 2182ms` / `2246ms`，
两次都看到绿色通知，标记正常落盘。

**教训**：与宿主 UI 相关的副作用必须在「UI 就绪」之后执行，而「调用没抛异常」**不等于**
「用户看到了」；一次性提示这类不可重试的动作，尤其不能在副作用确认前就写下「已完成」标记。

**产物**：`spw-folia-0.5.0.spmod`，15,737,961 B / 4,007 项，`Plugin-Version: 0.5.0`，内嵌 Folia 0.7.26，
17 种样式。上游与宿主均未变动（宿主 exe 178,688 B）。

**自我约束**：这条通知是 v0.3.2（issue #9）「启动不弹成功提示」规则的**唯一例外**，且仅限本版本。
0.5.1 起请勿把 `NOTICE_VERSION` 顺手改成当前版本号。
